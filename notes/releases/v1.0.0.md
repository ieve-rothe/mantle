# Mantle v1.0.0 Release Notes

> **Status**: In Progress — this document will be updated as breaking changes accumulate before the v1.0.0 baseline.

## Overview

Mantle v1.0.0 establishes a clean baseline for the framework, removing legacy subsystems that have been superseded by better approaches. Consumer applications upgrading from v0.x will need to make the changes described below.

---

## Breaking Changes

### 1. Logger Infrastructure Removed (TKT-001)

**What changed**: The abstract `Logger` class hierarchy (`Logger`, `FileLogger`, `DetailedLogger`) and the `app_logger.cr` namespace file have been removed from Mantle.

**What was removed**:
- `Mantle::Support::Logger` (abstract class)
- `Mantle::Support::FileLogger`
- `Mantle::Support::DetailedLogger`
- `Mantle::Support::Log` (moved — see migration below)
- `src/mantle/support/app_logger.cr`
- `src/mantle/support/logger.cr`

**Why**: The per-turn conversation logger (`Logger`/`FileLogger`/`DetailedLogger`) was superseded by `Mantle::Clients::LoggingClient`, which provides structured JSONL receipts for every LLM call with richer data (timestamps, latency, token counts, sequence tracing). The `app_logger.cr` file was a one-liner defining a logging namespace that still required consumer-side setup — not worth the file or the cognitive overhead.

**Impact on consumer applications**:

1. **Flow constructors no longer accept a `logger` parameter**:
   ```crystal
   # Before (v0.x)
   flow = Mantle::Flows::ChatFlow.new(context_manager, client, logger)
   flow = Mantle::Flows::ToolEnabledChatFlow.new(context_manager, client, logger)

   # After (v1.0.0)
   flow = Mantle::Flows::ChatFlow.new(context_manager, client)
   flow = Mantle::Flows::ToolEnabledChatFlow.new(context_manager, client)
   ```

2. **`Mantle::Support::Log` moved to `Mantle::Log`**:
   ```crystal
   # Before
   Mantle::Support::Log.info { "message" }

   # After
   Mantle::Log.info { "message" }
   ```

3. **If you subclassed `Mantle::Support::Logger`** (e.g., `class AppLogger < Mantle::Support::DetailedLogger`):
   - These classes no longer exist in Mantle
   - Move the logger implementation into your application code
   - The `FileLogger` and `DetailedLogger` source can be copied if still needed

4. **Application logging setup** — configure Crystal's built-in Log framework:
   ```crystal
   ::Log.setup do |c|
     backend = ::Log::IOBackend.new(io: File.new("app.log", "a"))
     c.bind("mantle", :debug, backend)
   end
   ```

5. **Per-call LLM logging** — use `LoggingClient` instead:
   ```crystal
   base_client = Mantle::Clients::OllamaClient.new(model_config)
   client = Mantle::Clients::LoggingClient.new(base_client, "logs/llm_receipts.jsonl")
   ```

### 2. MarkdownFormatter Relocated to Salamander (TKT-002)

**What changed**: `MarkdownFormatter` has been removed from Mantle (`Mantle::Support::MarkdownFormatter`) and relocated to Salamander (`Salamander::UI::MarkdownFormatter`).

**What was removed**:
- `Mantle::Support::MarkdownFormatter` (`src/mantle/support/markdown_formatter.cr`)
- `spec/markdown_formatter_spec.cr`
- `benchmarks/markdown_formatter_benchmark.cr`

**Why**: Formatting Markdown for terminal output is a presentation/UI layer responsibility (belonging to client applications like Salamander), not a core LLM engine capability. Relocating it prevents terminal ANSI escape sequence logic from leaking into the core engine.

**Impact on consumer applications**:
- Replace any references to `Mantle::Support::MarkdownFormatter` with `Salamander::UI::MarkdownFormatter` or an application-level UI formatter.

### 3. Global `Mantle.on_status_update` Removed (TKT-003)

**What changed**: The global singleton status callback `Mantle.on_status_update`, `Mantle.emit_status`, and `src/mantle/support/status.cr` have been removed. In addition, the stdlib `require "set"` in `status.cr` was eliminated. Status updates are now registered via instance-level `on_status` properties on `Flow` and `ContextManager`.

**What was removed**:
- `Mantle.on_status_update` and `Mantle.emit_status`
- `src/mantle/support/status.cr`
- `spec/mantle/status_spec.cr`
- `require "set"`

**Why**: Global singletons prevent safe multi-instance concurrency and pollute framework-level state. Attaching status callback handlers to individual `Flow` and `ContextManager` instances provides isolated status handling and eliminates global state. Storage components (`ContextStore`, `MemoryStore`) no longer emit UI status callbacks.

**Impact on consumer applications**:
1. **Pass `on_status` to `Flow` or `ContextManager` instances**:
   ```crystal
   # Before (v0.x)
   Mantle.on_status_update = ->(flag : Symbol) { ... }
   flow = Mantle::Flows::ChatFlow.new(context_manager, client)

   # After (v1.0.0)
   flow = Mantle::Flows::ChatFlow.new(context_manager, client, on_status: ->(flag : Symbol) { ... })
   # OR set via property accessor:
   flow.on_status = ->(flag : Symbol) { ... }
   context_manager.on_status = ->(flag : Symbol) { ... }
   ```

### 4. Model Thinking Tag Normalization (TKT-004)

**What changed**: `<think>` tag parsing and extraction has been moved directly into client response normalization (`Mantle::Clients::LlamaClient` and `Mantle::Clients::Response`). Raw response output is now automatically parsed and sanitized, populating `response.content : String?` with clean content and `response.thinking : String?` with extracted thinking content.

**What was added/updated**:
- `Mantle::Support::Text.extract_thinking(raw_text : String) : {String, String?}`
- `Mantle::Support::Text.strip_thinking(raw_text : String) : String` (now delegates to `extract_thinking`)
- `Mantle::Clients::Response#initialize` (automatically normalizes content and extracts thinking if `<think>` tags are present)
- `Mantle::Clients::LlamaClient` streaming & standard parsers (run raw body text through `extract_thinking` prior to building `Response`, preferring native API thinking if present)

**Why**: LLMs (such as DeepSeek-R1, Qwen-Thinking, or local Ollama models) often output reasoning thoughts inside `<think>...</think>` tags embedded directly in their text response. Moving parsing into client response normalization ensures that downstream components (`ChatFlow`, `ToolEnabledChatFlow`, memory summarizers, subagent runners, context stores) only ever handle clean assistant content without unparsed `<think>` tag cruft, while preserving full access to `.thinking`.

**Impact on consumer applications**:
- Applications no longer need to manually strip `<think>...</think>` tags from `response.content`.
- Handles closed tags (`<think>foo</think>bar`), multiline thinking, unclosed/truncated tags (`<think>foo` due to token limits), and tagless text automatically.
- Consumer code accessing `response.thinking` will now receive extracted thinking content regardless of whether the provider emitted native thinking fields or inline `<think>` tags.

### 5. `LlamaClient` Renamed to `OllamaClient` (TKT-005)

**What changed**: `Mantle::Clients::LlamaClient` has been renamed to `Mantle::Clients::OllamaClient`. As part of the Mantle v1.0.0 cleanup, no backwards-compatibility alias has been retained.

**What was changed/removed**:
- `Mantle::Clients::LlamaClient` (completely removed)
- `Mantle::Clients::OllamaClient` (canonical replacement)

**Why**: The client's wire protocol (`keep_alive`, options sub-object, NDJSON stream format) is explicitly Ollama-specific. Renaming avoids ambiguity and confusion as additional LLM provider backends (e.g. vLLM, llama-server, OpenAI) are introduced.

**Impact on consumer applications**:
- Replace all occurrences of `Mantle::Clients::LlamaClient` with `Mantle::Clients::OllamaClient`:
  ```crystal
  # Before (v0.x)
  client = Mantle::Clients::LlamaClient.new(model_config)

  # After (v1.0.0)
  client = Mantle::Clients::OllamaClient.new(model_config)
  ```

### 6. LoggingClient Concurrency & Async Disk I/O (TKT-005)

**What changed**: File locking and disk I/O for `LoggingClient(T)` have been overhauled:
1. **Unparameterized Mutex**: The file lock has been moved from the generic class `LoggingClient(T)` into the unparameterized module `Mantle::Clients::ReceiptWriter`. In Crystal, generic class variables are scoped per specialization; moving the lock to an unparameterized module ensures that multiple client specializations (e.g. `LoggingClient(OllamaClient)` and `LoggingClient(MockClient)`) logging to the same file target share the exact same lock.
2. **Dedicated Background Logger Fiber**: File writes are no longer executed synchronously in the calling fiber. Receipts are enqueued to a buffered `Channel(ReceiptTask)` consumed by a dedicated background writer fiber.
3. **Deterministic Flush**: A `ReceiptWriter.flush` (and `LoggingClient#flush`) method is provided which strictly blocks until the buffered channel is empty and all prior queued receipts have completed writing and flushing to disk.

**Impact on consumer applications**:
- Subagents and batch test pipelines running high-frequency requests no longer suffer from synchronous disk I/O bottlenecks.
- In test suites or shutdown sequences where deterministic file state is required, call `Mantle::Clients::ReceiptWriter.flush` or `client.flush`:
  ```crystal
  client.execute(messages)
  client.flush # or Mantle::Clients::ReceiptWriter.flush
  ```
